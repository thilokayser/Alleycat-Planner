# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Alleycat Dispatch is an organizer tool for alleycat races (bike checkpoint races): create events, place checkpoints on a map, print bib numbers/spokecards, run finish-line check-in, keep a leaderboard, export a manifest as PDF. It ships as two self-contained HTML files (local/server storage variants) opened directly in a browser — but those files are **generated**, not hand-edited. See Architecture below before touching anything.

## Commands

No `npm install`, no dependencies — `build.js` is plain Node.

- **Build the app**: `node build.js` — reads `src/` and `templates/`, writes `dist/alleycat-dispatch-local.html` and `dist/alleycat-dispatch-server.html`. Run this after every source change before testing in a browser.
- **Run the app**: open `dist/alleycat-dispatch-local.html` (or `dist/alleycat-dispatch-server.html`) directly in a browser after building.
- **Run tests**: paste the contents of `test-suite.js` into the browser console of a running `dist/` build, then call `runAlleycatTestSuite()`. It exercises event CRUD, all checkpoint types, teams, the full check-in flow, leaderboard, manifest, PDF export, and storage roundtrip end-to-end.
- **PHP backend local testing**: no automated way — run `php-backend/` against a local PHP+MySQL setup (e.g. XAMPP) and point `dist/alleycat-dispatch-server.html`'s setup screen at it.

## Architecture

### Never edit `dist/*.html` directly

`dist/` is Git-ignored, fully generated output — `node build.js` overwrites it every time. **All source changes go in `src/` or `templates/`.** If you're about to edit an HTML file and its path starts with `dist/`, stop and find the corresponding file in `src/core/`, `src/storage/`, `src/styles/`, or `templates/` instead.

`build.js`'s `CORE_FILES` order is not load-bearing — almost everything is hoisted function declarations, so cross-module call order doesn't matter. It only matters that `{{STORAGE_JS}}` and `{{CORE_JS}}` both land before the trailing `init();` call in the template.

### The storage-capability seams

Everything in `src/core/*` must build to **byte-identical** output across both variants — any variant-specific behavior belongs in `src/storage/storage-{local,server}.js` instead, exposed through one of these seams that shared code calls into:

- **`initStorageBackend()`** — called first thing in `ui-headquarter.js`'s `init()`. Local: awaits `initSqliteStorage()`, always returns `true`. Server: returns `false` and renders the PHP setup screen if unconfigured, `true` otherwise. `init()` bails out if this returns falsy.
- **`renderStorageDashboardExtras()`** — called from `dashboard.js`'s `renderDashboard()` toolbar. Local: returns the SQLite import/export buttons HTML (only when `!hasSharedStorage`). Server: returns `''`.
- **`exportBackupBlob(evt)`** — called from `data-safety.js`'s `triggerBackupNow()`. Local: returns `{blob, filename}` with a `.sqlite` export of the whole local database. Server: returns `{blob, filename}` with a `.json` export of just `evt`. Both return `null` when `hasSharedStorage` (Artifact-managed storage — no meaningful local single-file backup story there), which makes the whole Auto-Backup feature (and its Settings UI) a no-op/hidden in that mode.

If you add a new variant-specific behavior, follow this pattern rather than branching on `hasSharedStorage`/`typeof sqlDb` etc. inside a `core/*` file. Note that offline map-tile caching (`offline-tiles.js`) deliberately does **not** use this seam pattern — it's a raw, per-device `indexedDB` cache independent of the app's storage backend, so it works identically (and needs no seam) in both variants.

### Storage abstraction

All persistence goes through three async functions with a stable contract regardless of backend: `storageGet(key)` → `{value: string} | null`, `storageSet(key, value)` → `bool`, `storageDelete(key)` — defined per-backend in `src/storage/*`. Everything above this layer (`loadEvent`, `saveCurrentEvent`, `loadEventsIndex`, `debouncedSave`, etc., in `ui-headquarter.js`) is backend-agnostic.

### App structure (single global `state`)

- `state` (top of `ui-headquarter.js`) holds `currentEvent`, `eventsIndex`, `view`, `appSettings`, etc. There is no framework — `render()` is called after any state change and re-renders the active view by toggling `.active` on `#view-*` containers and calling the matching `render<ViewName>()` function.
- **`CHECKPOINT_TYPES`** (`checkpoint.js`, a mutable `let`) is the single source of truth for checkpoint kinds. User-defined custom types get merged in at load time from `checkpointTypes:custom` in storage and must stay after the built-in types (`BUILTIN_CHECKPOINT_TYPE_KEYS`) when persisted.
- **`THEMES`** and **`ICON_PACKS`** (`ui-headquarter.js`) drive the Settings page; themes are pure CSS variables swapped via `data-theme` on `<html>` (see `src/styles/themes.css`), icon packs lazy-load their CDN (Font Awesome / Material Symbols) on selection.
- Escaping conventions are deliberate and must be preserved when adding new export paths: `escapeHtml()` (`utils.js`) for all interpolated HTML, a local `esc()` inside `exportRouteGPX()` for XML, and `csvEscape()` for CSV — the latter also neutralizes leading `= + - @` to prevent formula-injection when the export is opened in Excel/Sheets.
- **i18n**: every visible UI string goes through `t('namespace.key', params)` (`i18n.js`) rather than being hardcoded — only `de` is populated today, but the structure is translation-ready. Never wrap `t()` calls around user-entered content (checkpoint/team/category names, clues) — those stay raw. Watch for arrow-function params named `t` shadowing the global `t()` inside `.map()` callbacks (rename to e.g. `ct`/`tm`/`th`).
- **Race status machine** (`race-state.js`): `evt.status` moves `planning → ready → running → completed` (backward always allowed, with a confirm). Forward transitions are validated (`markReady` blocks without ≥1 checkpoint + `expectedRiders` set; `completeRace` warns about riders without a finish time, excluding those marked DNF/DNS); only reachable via `onStatusSelectChange()` (topbar dropdown) or the blocking start-time dialog (`checkStartDialog()`, polled every second from `init()`, renders into `#start-dialog-root` — independent of `render()`/the active view since it must persist across navigation). `isCpLocked(evt)` gates checkpoint structure edits in `checkpoint.js`'s `renderSidebar()` once `status` is `running`/`completed` (with a `cpLockOverride` escape hatch during `running`) — this is the only read-only enforcement in place; other views do not yet respect race status.
- **Rider race status** (`rider.raceStatus`, `''|'dnf'|'dns'`, set via `setRiderRaceStatus()` in `checkin.js`): independent of `finishTime` — `riderStatusBadgeHtml()` checks it before falling back to curfew logic. Confirming a rider at the finish (`confirmRiderAtFinish()`) always clears it.
- **Category groups** (`category.js`): `evt.categoryGroups = [{id, name, options[], sortOrder}]`, orthogonal to and independent of the Teams system. `rider.categories = {[groupId]: selectedOption}`. Option values are raw user text (from presets or custom input) and never go through `t()` — same rule as checkpoint/team names. Renaming or deleting an option cascades into every rider's assignment; deleting a group clears the corresponding key on every rider.
- **Team scoring mode** (`evt.teamScoringMode`, `'bestTime'|'allMustFinish'`, set in `rider.js`'s Teams section): `computeTeamStats()` in `team.js` computes `bestTime`/`worstTime`/`allFinished` per team and sorts accordingly — `bestTime` ranks by the fastest member's finish time, `allMustFinish` requires every member to have finished and ranks by the slowest member's time (teams with an unfinished member sort last).
- **Checkpoint order mode** (`evt.checkpointOrderMode`, `'frei'|'fest'`, toggle in `checkpoint.js`'s `renderSidebar()`): purely advisory in `'frei'`. In `'fest'`, `checkin.js`'s `checkOrderBeforeComplete()` gates `onCheckinToggleCheckpoint`/`onCheckinSetScore` — completing a checkpoint out of `order` sequence prompts a confirm; accepting appends `{checkpointId, at}` to `rider.checkpointOrderOverrides` as an audit log. Distance (`computeRouteLegs()` in `utils.js`, plain Haversine on CP coordinates, no API call) is only shown in `'fest'` mode, per-leg between consecutive `cp-row`s plus a total — intentionally omitted in `'frei'` mode since sequence-less checkpoints have no meaningful "route length".
- **Overview tab / dashboard widgets** (`dashboard.js`): a per-event "Übersicht" tab (`state.view === 'overview'`, `openOverview()`/`renderOverview()`), separate from the HQ home view (`state.view === 'dashboard'`, event list). `DASHBOARD_WIDGET_KEYS` is the widget catalog (`statusTiles`/`cpLoad`/`recentActivity`/`categoryDistribution`/`miniLeaderboard`/`countdown`/`todos`); each has a `compute*`/`render*Widget` pair. Visibility and order are stored per-event on `evt.dashboardWidgetOrder`/`evt.dashboardWidgetVisibility` (defaults: statusTiles/cpLoad/countdown visible, rest hidden) and edited via the in-page settings panel (`toggleOverviewSettings()`, checkbox + up/down reorder — no drag-and-drop). `computeDashboardTodos()` surfaces only structural completeness gaps (missing checkpoints/positions/start time/capacity/unassigned category groups/unprinted bibs+spokecards/no manifest yet/checkpoints without personnel) — no time-threshold warnings. The countdown widget ticks live via `startOverviewTick()`/`updateOverviewCountdown()` (same self-stopping `setInterval` pattern as `checkin.js`'s live countdown, keyed on `state.view !== 'overview'`), patching `#overview-countdown-value` directly rather than a full re-render.
- **Per-checkpoint lock** (`cp.locked`, toggled via `toggleCpLocked()` in `checkpoint.js`): independent of and orthogonal to the race-status CP lock (`isCpLocked(evt)`) — protects a single checkpoint's position/type/clue/staff from edits (and blocks `moveCp`/`duplicateCheckpoint`/`confirmDeleteCp`) regardless of race status, for e.g. a scouted-and-confirmed position. The sidebar row computes `itemLocked = isCpLocked(evt) || cp.locked` and swaps in the same read-only `cp-edit-readonly` block used for the race-status lock when either is true; only UI-gated (consistent with the existing race-status lock), not re-checked inside every handler, except where the whole point of the flag is to block a specific action (`moveCp`, `confirmDeleteCp`, `duplicateCheckpoint`, `addCpStaff`, `toggleCpLocked` itself all re-check defensively).
- **Checkpoint list enhancements** (`checkpoint.js`): each `cp-row` shows a live check-in load badge (riders whose `completed` includes the checkpoint), a time-window status badge (`cpTimeWindowStatus()` → `upcoming`/`open`/`closed`, computed at render time, not ticking), a personnel count badge, and duplicate/lock quick-action icons. `state.cpListGroupBy` (`'order'|'type'`) toggles between the normal sequence list and CHECKPOINT_TYPES-grouped sections (`renderCpListRows()`) — drag/move controls are hidden in the grouped view since reordering across type groups isn't meaningful. Clicking a row also `map.flyTo()`s to that checkpoint (`selectCp()`).
- **Checkpoint personnel** (`cp.staff = [{id, name, phone, role, shiftNote, notes}]`, CRUD via `addCpStaff()`/`removeCpStaff()`/`onCpStaffFieldChange()`): edited inline in the checkpoint's edit form, phone numbers rendered as `tel:` links. **Never** surfaced in `exportManifestPDF`/`buildRiderSheetDoc`/`buildSpokeCardsDoc` (rider-facing) — the only export that reads `cp.staff` is the separate, organizer-only `buildStaffBriefingDoc()`/`exportStaffBriefingPDF()` in `export-pdf.js`, reachable from the editor sidebar footer.
- **Beamer view** (`beamer.js`): a fullscreen, forced-dark route at `#/beamer/<event-id>`, completely outside the normal `state`/`render()` SPA machinery — `init()` checks `isBeamerRoute()` first and branches to `initBeamer()`, which hides `#app` and shows the sibling `#beamer-root` container (added in both templates). Local variant: "separate" means a second browser tab on the same origin — real cross-device only works via the server variant's PHP backend, same route/code either way since both go through the storage-agnostic `loadEvent()`. Own lightweight `beamerState` object (`{eventId, evt, phase, audioBlocked}`, phase `'countdown'|'go'|'live'`) is kept separate from the HQ's global `state` on purpose. Sync: `getBeamerChannel()` wraps a `BroadcastChannel('alleycat-beamer')` (`null` if unsupported); `broadcastRaceStart()` is called from `race-state.js`'s `startRace()` for an instant GO-trigger reaction, `broadcastEventUpdated()` is called from `ui-headquarter.js`'s `saveCurrentEvent()` after every successful save so any open beamer tab reloads the event — a 7s `setInterval` poll (`loadBeamerEvent()`) is the fallback if a broadcast was missed. `triggerGoSequence()` shows the GO overlay, awaits `AlleycatSounds.play('race_start')`, shows a "click to activate" overlay (`dismissBeamerAudioBlock()`) only if a sound was registered but blocked by autoplay policy, then auto-transitions to the live phase after 4s. Live phase re-derives rank/underway/DNF-DNS groupings from scratch on every update via `sortBeamerRiders()` (no incremental diffing) and ticks only the race-clock text node (`updateBeamerTick()`) every second, not the whole table — deliberately, so a beamer screen doesn't flicker/re-layout for an audience once results start rendering. Since setting `location.hash` triggers `init()`'s own `hashchange`→`location.reload()` listener, **never mutate `location.hash` from within `test-suite.js`** (would abort the running suite) — route-parsing is only exercised there via the safe non-navigating baseline (`isBeamerRoute()`/`beamerEventIdFromHash()` return false/null outside the route).
- **Sound-hook module** (`sound-hook.js`, deliberately generic/reusable, not beamer-only): `AlleycatSounds.register(key, dataUrl)`/`.play(key)` (returns a `Promise<boolean>`, resolves `false` — never throws — for an unregistered key or an autoplay-blocked/failed play)/`.isRegistered(key)`/`.unregister(key)`. `SOUND_EVENTS` is the full catalog key→description map (`race_start` is the only one wired to UI today; the rest exist so later phases don't need a data-model migration). Per-event storage: `evt.soundHooks = {[key]: {name, dataUrl}}` (base64, 2MB upload cap enforced in `onSoundHookFileChange()`), wired into the live `AlleycatSounds` registry via `registerEventSounds(evt)` (called on every HQ/beamer event load). UI lives in the Overview tab (`renderBeamerOverviewSection()` in `beamer.js`, called from `dashboard.js`'s `renderOverview()`), not a dedicated settings page, since sounds are per-event data, not app-wide.
- **Auto-backup** (`data-safety.js`): `startAutoBackup()` runs one `setInterval` for the app's lifetime (interval length from `state.appSettings.autoBackupIntervalMinutes`, default 10, restarted via `onAutoBackupIntervalChange()` on change); the tick (`runAutoBackupTick()`) itself no-ops unless `state.currentEvent.status === 'running'` — matches the doc spec of "only while running" without needing to start/stop the timer on every status transition. `triggerBackupNow(silent)` calls the `exportBackupBlob()` seam, triggers a real `<a download>` click, and sets `evt.lastBackupAt`; the first-ever download in a session shows a one-time `alert()` warning about repeated browser download prompts (`state.appSettings.autoBackupHintShown`). Whole feature (Settings section + the Overview "Letztes Backup" status line, see `renderBackupStatusLine()`) is hidden when `hasSharedStorage`, since `exportBackupBlob()` returns `null` there.
- **Beforeunload warning + running-hint** (`data-safety.js` / `ui-headquarter.js`): a dedicated `beforeunload` listener (separate from `ui-headquarter.js`'s pre-existing one, which only does `flushPendingSave()`) calls `e.preventDefault()` when the current event's `status === 'running'` — browsers only show a generic confirmation text, not `e.returnValue`'s content, so a small `⚠ Tab bitte offen lassen` hint (`.running-hint`) is also rendered into `renderTopbar()` whenever running, for visibility before the user even tries to close the tab.
- **Wake Lock** (`data-safety.js`): `requestWakeLock()`/`releaseWakeLock()` wrap the `navigator.wakeLock` API (no-op/`false` if unsupported — Safari needs iOS 16.4+, no fallback hack). `syncWakeLockForView()` is called at the end of `ui-headquarter.js`'s `render()` and holds the lock only while `state.view === 'checkin'` on a `running` event (guarded so it doesn't re-request on every re-render while already held); `beamer.js`'s `initBeamer()` requests it unconditionally once, independent of that sync function since the beamer never returns to the normal SPA view machinery within its tab.
- **Storage APIs** (`data-safety.js`): `requestPersistentStorage()`/`getStorageEstimate()` wrap `navigator.storage.persist()`/`.estimate()` (both resolve `null` if unsupported). Persist is requested exactly once per browser (`localStorage['alleycat:persistRequested']` guard), armed via `armPersistentStorageRequest()` in `init()`, but only actually fires on the next real `click` anywhere in the document (`{once: true}` listener) since some browsers only honor `persist()` inside a user-gesture. The estimate (plus a "Persistenten Speicher anfragen" button) is shown in Settings (`renderDataSafetySection()`), refreshed async after `renderSettings()` writes its placeholder markup — same pattern as `refreshTileCacheTotal()` below.
- **Offline map-tile cache** (`offline-tiles.js`): a **separate, raw `indexedDB` store** (`alleycat-tiles`/`tiles`, keyed `"{z}/{x}/{y}"`, values are tile `Blob`s) — deliberately outside the app's `storageGet/Set/Delete` abstraction since it's a per-device browser cache, not app data, and therefore needs no storage seam (identical code path in both variants). `map.js`'s tile layer is `createOfflineTileLayer(...)` instead of a plain `L.tileLayer(...)`: its `createTile()` checks the cache first, falls back to network, and falls back again to a grey SVG placeholder tile (`TILE_GREY_PLACEHOLDER`) on a network failure — `detectRetina` is intentionally **off** so the live map's tile requests always resolve to the exact same `z/x/y` key the offline-cache download step used (a `{r}`/`@2x` variant would silently miss the cache). Downloading: `tilesForEvent(evt)` computes a checkpoint bounding box +500m buffer (`computeCheckpointBoundsWithBuffer()`) across zoom 13–17 (`tilesInBounds()`, standard Web Mercator tile-index math), `cacheTileList()` fetches with 6-way concurrency and skips tiles already cached. Settings' "Offline-Bereitschaft" section (`renderOfflineReadinessSection()`) lazily loads every event via `refreshOfflineReadiness()` (eventsIndex entries don't carry `status`, so this needs a full `loadEvent()` per event) filtered to `ready`/`running`, lets the organizer check events (`offlineUiState.selected`), shows a live tile/MB estimate, and caches via `cacheSelectedOfflineEvents()` (which also shows the one-time iOS/Safari storage-eviction hint, `state.appSettings.offlineCacheHintShown`, and sets `evt.tileCacheUpdatedAt`). Staleness (`offlineTileCacheStaleness()`, `>24h` → `'warn'`, `>3 days` → `'danger'`) feeds a `severity`-tagged entry into `computeDashboardTodos()`, rendered with a colored `todo-warn`/`todo-danger` class in `renderTodosWidget()` — the only todo severity levels in the app so far. **License note**: tiles are fetched from CARTO's Voyager basemaps (`{s}.basemaps.cartocdn.com`, same provider `map.js` already used pre-Phase-9), which serve permissive CORS (`Access-Control-Allow-Origin: *`, verified) — fine for this app's moderate, organizer-triggered, once-per-event caching; not a general recommendation to hammer their tiles.
- **PDF-Baukasten** (`pdf-blocks.js`): `evt.pdfBlocks = [{id, type, targetDocuments[], enabled, sortOrder, content, config{}}]`, 7 built-in `PDF_BLOCK_TYPES` (`waiver`/`rules`/`sponsors`/`checkpoint_list`/`notes`/`custom_text`/`emergency_info`). Deliberately **not** a full block-driven document renderer (the doc's own sketch implies `renderDocument()` composing the *entire* PDF from blocks) — that would mean rewriting the existing, already-tested Manifest table and fixed-size (63.5×88.9mm) Spokecards card layouts from scratch, high regression risk for a nice-to-have. Instead, enabled blocks are **appended as extra pages** after a document's existing content — `appendPdfBlocks(doc, evt, targetDocType)` in `export-pdf.js`, called from `exportManifestPDF()` (both the empty-columns early-return and the normal save path) and from `buildSpokeCardsDoc()` (so it's included whether reached via `exportSpokeCardsPDF()`/`printSpokeCardsPDF()`/`buildRiderSheetDoc()`'s sibling doc) — `targetDocuments` only ever contains `'manifest'`/`'spokecards'` (Startnummern/`buildRiderSheetDoc` and the organizer-only Personal-Briefing are deliberately excluded, matching the doc's 2-checkbox UI spec). `appendPdfBlocks()` is **unit-agnostic**: the manifest doc uses jsPDF `unit:'pt'`, the spokecards doc uses `unit:'mm'` — rather than hardcoding pt-based margins (which would be tiny/huge depending on which doc called it), margins/line-heights are fractions of `doc.internal.pageSize.getWidth()/getHeight()` (queried in whatever unit that doc uses); only `setFontSize()` stays a fixed pt value, since jsPDF font size is always in points regardless of document unit. Block content is **not** real Markdown despite the doc calling the waiver field "Markdown-Textfeld" — it's plain text with blank-line-separated paragraphs and `doc.splitTextToSize()` word-wrap, consistent with how checkpoint clues/notes are handled elsewhere (no Markdown parser exists in this codebase). Panel UI (`renderPdfBlocksPanel()`) is rendered into the Manifest view's toolbar (`togglePdfBlocksPanel()`/`state.pdfBlocksPanelOpen`, parallel to the pre-existing column-customize panel), with a discoverability hint + link in `rider.js` near the spokecards buttons since blocks can target that document too. JSON template export/import (`exportPdfBlocksJSON()`/`onImportPdfBlocksFile()`) mirrors `category.js`'s `exportCategoriesJSON()`/`onImportCategoriesFile()` pattern.
- **Spielmodi-Engine** (`rules-engine.js` + `game-modes.js`): the spec's own MVP call — "kein visueller Regel-Baukasten im UI, Engine bleibt intern generisch" — is implemented literally: `evaluateRules(evt, triggerType, context)` in `rules-engine.js` is the one generic dispatch every trigger point goes through (checkpoint check-in, finish, a 10s `on_tick` interval gated on `evt.status === 'running'`, and organizer "manual" actions like assigning a joker or advancing a Battle-Royale zone). It iterates `evt.gameModes.filter(m => m.enabled)`, looks up each mode's static rule list in `GAME_MODE_DEFS[mode.type]` (`game-modes.js`), and runs any `{trigger, condition, effect}` entries matching that trigger — an effect can veto the action that triggered it by returning `{block, message}` (used by `time_window`/`zone_active` to reject an out-of-window/out-of-zone check-in). Adding a later preset is meant to only need a new `GAME_MODE_DEFS` entry, never a change to the evaluator itself. All 7 non-deferred presets from the doc are implemented this way: `time_window` (enforces the pre-existing per-checkpoint time window that was previously advisory-only), `first_n` (Bonus-CPs — reuses the existing `cp.mandatory === false` flag as the "bonus checkpoint" marker instead of adding a new field, awards `config.pointsByRank` by arrival rank), `prerequisite` (Geheime CPs — `cp.gameHidden`/`cp.gameRevealPrerequisiteCpId`, reveal state is event-level in `evt.ruleRuntimeState.revealedCheckpoints`, not per-rider, matching the doc's `rule_runtime_state` schema choice — once any rider clears the prerequisite, the checkpoint is revealed for everyone), `zone_active` (Battle Royale — zone center is the centroid of all checkpoints, no extra map-picking UI; `isCpClosedByZone()` computes closed/open on the fly from `evt.ruleRuntimeState.zoneStage` + `haversineDistanceKm()`, nothing about "closed" is persisted per-checkpoint; `config.triggerMode` is `'scheduled'|'manual'|'both'`, scheduled advancement is a catch-up loop in `maybeAdvanceZoneBySchedule()` so a tab that was closed across multiple stage thresholds jumps straight to the correct stage on the next tick), `rider_flag` (Wildcard/Joker — `rider.gameFlags.jokerCpId`, `isCpSatisfiedForRider()` treats it as equivalent to a real completion in mandatory-checkpoint checks, checked via a dropdown in the check-in card only when the mode is enabled), `sequence_match` (Kettenreaction — on a perfect `'fest'`-order finish with no `checkpointOrderOverrides`, awards a bonus equal to `basePoints * (multiplier - 1)`; existing `sequence_match`-sourced ledger entries are removed before recomputing so re-confirming a finish via undo doesn't compound the bonus), `sudden_death` (eliminates inactive riders past `config.cutoffMinutes` if idle longer than `config.inactivityMinutes` — reading `lastCheckpointTimeForRider()`, which only works because `checkin.js` now records `rider.checkpointTimes[cpId]` on **every** checkpoint completion, not just when `cp.timeWindowEnabled`, a deliberate widening of that field's original purpose). "Kopfgeld" (needs live leader recalculation + rider-tag interaction) is explicitly out of scope per the doc's own phase note, and its `is_leader` condition type is unused. **Numeric config gotcha**: never read a mode's numeric config field with `config.x || default` — an intentional `0` (e.g. "eliminate immediately") is falsy and would silently fall back to the default; use the `numOr(value, fallback)` helper (`Number.isFinite` check) instead, in both the effect logic and the settings-form input handlers. Points/scoring: `evt.pointsLedger = [{id, riderBib, checkpointId, amount, reason, source, createdAt}]` (keyed by `riderBib`, not a rider `id` — riders in this app have no separate id field, `bib` is the stable identifier used everywhere), `awardPoints()`/`removeLedgerEntries()`/`pointsForRider()`/`ledgerEntriesForRider()` in `rules-engine.js`. Enabling a points-awarding mode (`first_n`/`sequence_match`) shows the doc's required confirm dialog and flips `evt.scoringMode` to `'points'`; `leaderboard.js` then ranks by `sortRidersByPoints()` (points desc, finish time as tiebreaker only) instead of `sortRidersForOverview()`, adds a "Spielmodi-Punkte" + "Zeit" column pair, and clicking the points badge (`showPointsLedger()`) lists that rider's ledger entries via `alert()` — satisfying the doc's "Punkte-Herkunft je Fahrer einsehbar" requirement without a new modal system. `rider.raceStatus` gained a fourth value, `'eliminated'` (alongside the existing `''|'dnf'|'dns'`), threaded through every `raceStatus !== 'dnf' && raceStatus !== 'dns'` exclusion check across `beamer.js`/`dashboard.js`/`leaderboard.js`/`race-state.js` so eliminated riders are treated like DNF/DNS everywhere finished/underway counts matter.

### `php-backend/`

Separate deployment target (PHP + MySQL, no framework) consumed only by the server variant. `install.php` is a one-time web installer (creates the `kv` table, generates an API key, writes `config.php` — then must be deleted from the server). `api.php` is the REST endpoint (`GET`/`POST`/`DELETE` via `?key=...`, auth via `X-Api-Key` header) mirroring the `storageGet`/`storageSet`/`storageDelete` contract above. `config.php` holds plaintext DB credentials and is gitignored — never commit it.
